- [x] trimmed the `Entry` struct to a single source of truth: dropped the materialized `Title`/`Tags` fields (they duplicated `fm`) and the `Name` field (it duplicated `basename(Path)`; replaced by a computed `base()` accessor used by Resolve, reserved-file checks, and the spaced-name lint), following the `timestamp` precedent (read/compute on demand, never stored). Canonical columns for text `list`/`search` + csv/tsv are now just `_path,type` (the two fields every entry is guaranteed to have); title/tags/status/etc are json-only (emitted verbatim from `fm`). `wiki tags`/`status` tag counts read via `parse.Strings`/`TagCounts`; `read` json is `{_path,type,body}`; `SearchHit` dropped `title`. Kept `Type` (the one required, validated field, and the classifier shown in every listing).
- [x] bug fix: frontmatter `name:`/`path:` no longer clobbered in `--format json`. `MarshalJSON` merged frontmatter with structural keys and let the structural `name`/`path` win, so a `person`'s `name: Dana Smith` reported as the filename (and a `path:` field was lost), while `--where name=…` read the frontmatter correctly, the two disagreed. The entry's file path now lives under the reserved, underscore-prefixed key `_path` (a leading `_` never appears in frontmatter), so every real frontmatter key round-trips verbatim. The structural basename is dropped from output entirely (it is just `basename(_path)`); a frontmatter `name:` is the user's and passes through as `name`. Applied uniformly (Entry, `SearchHit`, `FileRewrite`, `read`, `outline`; csv/tsv headers too) so `_path` means the same thing in every command and format, no mixed convention. Frontmatter is emitted **verbatim** (dropped the old `type`/`title` re-serialization, which was a no-op copy, and the `tags`-only list coercion, which singled out one field against the opacity model): `list --format json` is now just your frontmatter plus `_path`. Matching still treats scalar and one-element list alike, but that lives in the query layer, not output.
- [x] `--where key=` / `key!=` (empty value) now test emptiness instead of being a degenerate no-op: `assignee=` is unset/blank (unassigned), `assignee!=` is present-and-non-empty (built on the empty==absent normalization in `parse.Strings`). A missing operator (`--where name`) or empty key stays the error. Answers "which are unassigned / teamless" without dropping to `jq`.
- [x] [`--where key!=value` (inequality)](/2-query-surface/010-where-negation.md): `--where` gained negation, so "not X" is expressible (`status!=done` for active work). Parse splits on the first `!=` (else the first `=`, so a value may itself contain `=`); `index.PropFilter` carries `Negate` and `matchesAll` inverts that clause. A missing key **matches** an inequality (an entry with no `status` is "not done"). Comparing against the **empty string tests emptiness**: `--where assignee=` is unset/blank (unassigned), `--where assignee!=` is present-and-non-empty; a missing operator (`--where name`) or empty key is still the error. Stays eq/neq only, no `<`/`>`/`OR` (richer reporting is a skill over `--format json`). `!=` is shell-safe: bash/zsh history expansion is exempt when `!` is immediately followed by `=`, and fish has no `!` expansion.
